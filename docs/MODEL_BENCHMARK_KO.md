# 번역 모델 벤치마크 (영어 → 한국어)

Thoth Reader에서 쓸 로컬 번역 모델을 고르기 위해, LM Studio에 올린 여덟 개 모델을 같은 글로 비교한 기록입니다. 개발 서적을 한국어로 읽는 용도를 기준으로 봤습니다.

측정일은 2026-11-14입니다. 샘플이 한 쪽 분량이라 결과는 경향을 보는 정도로 읽어 주세요. 품질 평가는 번역문을 직접 읽고 내린 판단이며, 자동 점수는 쓰지 않았습니다.

## 측정 조건

- **장비**: Apple M1 Max, 메모리 32GB
- **실행 환경**: LM Studio의 OpenAI 호환 API, 모든 모델 Q4_K_M 양자화
- **설정**: temperature 0, 스트리밍 응답, 문단당 출력 한도 1,500토큰
- **순서**: 모델을 하나씩 올려 측정하고 내린 뒤 다음 모델을 올렸습니다. 문단은 동시에 보내지 않고 하나씩 보냈습니다.
- **qwen3.8-27b**는 추론형 모델이라 앱과 같이 `reasoning_effort: "none"`으로 숨은 추론을 껐습니다.

### 샘플

*The Rust Programming Language* 4.1장 "What Is Ownership?"의 "Memory and Allocation" 부분에서 본문 7문단(409단어, 2,298자)을 골랐습니다. Rust 프로젝트가 MIT/Apache-2.0으로 공개한 글이라 원문을 그대로 실을 수 있습니다.

이 부분을 고른 이유는 개발 서적 번역에서 자주 틀리는 요소가 고루 들어 있기 때문입니다.

- 백틱으로 감싼 코드(`String::from`, `drop`, `allocate`, `free`)를 그대로 두는지
- "string literal", "scope", "garbage collector" 같은 용어를 일관되게 옮기는지
- 여러 절이 이어지는 긴 문장(문단 1, 4)의 뜻을 놓치지 않는지

강조용 밑줄 표시는 지우고 백틱은 그대로 두었습니다.

### 요청 방식

- **표준**: 긴 지시문(시스템 메시지)과 JSON으로 감싼 본문을 보냅니다. 앞 문단을 문맥으로 함께 보내서 용어와 문체를 이어 갈 수 있습니다. 일반 대화형 모델에 맞습니다.
- **단순**: 짧은 규칙 몇 문장 뒤에 본문을 붙인 메시지 하나만 보냅니다. 문맥은 보내지 않습니다. 번역 전용 모델에 맞습니다.
- **모델 고유 형식**: Rosetta 모델 카드가 안내하는 형식입니다. 시스템 메시지에 "Translate the user's text to Korean."과 어조를 적고, 사용자 메시지에는 본문만 넣습니다. Thoth Reader는 아직 이 형식을 지원하지 않습니다.

Thoth Reader에서는 번역 프로필의 "요청 방식"에서 표준과 단순을 고를 수 있고, 모델 이름을 보고 자동으로 선택됩니다.

## 모델별 평가

### hy-mt2-7b — 평소 읽기에 추천

LM Studio가 `hunyuan-dense` 구조의 7.5B 모델로 표시하는 번역 전용 모델입니다.

- **속도**: 한 쪽 29초. qwen3.8-27b보다 2.3배 빠르고, 첫 글자가 0.3초 만에 나옵니다.
- **품질**: 문장이 여덟 개 중 가장 자연스럽게 읽힙니다. 문단 4처럼 긴 문장도 한국어 어순에 맞게 다시 짰습니다.
- **형식 유지**: 코드, 합니다체, 굵게·기울임 태그, 쪽 넘김 표시를 모두 지켰습니다(별도 시험 10문단).
- **아쉬운 점**: "closing curly bracket"을 "괄호"로만 옮겼고, "scope"를 "범위"로 옮겨 qwen의 "스코프"와 용어가 다릅니다.
- **주의**: 표준 방식에서는 8문단 중 1문단이 JSON으로 돌아왔습니다. 단순 방식으로 써야 합니다.

### qwen3.8-27b — 정확도가 중요할 때 추천

27B 크기의 범용 대화형 모델입니다. 번역 전용이 아니어서 표준 방식의 긴 지시문과 문맥을 그대로 이해합니다.

- **품질**: 뜻을 가장 정확하게 옮기고, 앞 문단 문맥을 받아 용어가 일관됩니다. `statement`, `expression`처럼 헷갈리는 용어에 원어를 병기하기도 합니다.
- **속도**: 한 쪽 67초, 첫 글자까지 2.5초로 가장 느립니다. 500쪽 책이면 순서대로 번역할 때 9시간 남짓 걸립니다.
- **아쉬운 점**: "Rust은", "러스트"처럼 같은 낱말의 표기가 문단마다 흔들렸습니다.
- **메모리**: 19.4GB라 32GB 장비에서 다른 큰 프로그램과 함께 쓰기 빠듯합니다.

### YanoljaNEXT-Rosetta-12B-2510 — 품질은 좋지만 앱에서 아직 못 씀

야놀자넥스트가 Gemma 3 구조를 바탕으로 만든 12B 번역 모델입니다. 모델 카드에 따르면 JSON·YAML·XML 같은 구조화된 데이터를 구조를 유지한 채 번역하도록 만들어졌습니다.

- **품질**: 고유 형식으로 보내면 hy-mt2-7b와 비슷한 수준입니다. 용어 선택("스코프", "리스팅")은 개발자에게 더 익숙한 쪽입니다.
- **속도**: 한 쪽 30초.
- **아쉬운 점**: 문단 7에서 "러스토(Rust)"라는 오타가 나왔고, "Rust"와 "러스트"를 섞어 썼습니다.
- **앱에서 못 쓰는 이유**: 표준 방식에서는 JSON 전체를 번역해 돌려주고, 단순 방식에서는 규칙 문장까지 번역해 본문 앞에 붙입니다. 구조화된 데이터를 통째로 번역하도록 학습된 모델이라 그렇습니다. 앱이 고유 형식을 지원해야 쓸 수 있습니다.

### EXAONE-3.5-7.8B-Instruct — 빠른 범용 모델

LG AI연구원의 7.8B 범용 모델로, 한국어와 영어를 함께 학습했습니다.

- **속도**: 한 쪽 18초로, 정상 출력 7/7인 모델 중 가장 빠릅니다.
- **호환성**: 표준과 단순 두 방식 모두 7/7로 동작했습니다. 단순 방식이 코드를 더 잘 지켰습니다. 표준 방식에서는 `allocate`를 `할당`으로 옮기고 `::` 같은 기호가 남았습니다.
- **품질**: 뜻은 대체로 맞지만 어색한 문장이 있습니다. 예를 들어 문단 4의 "이것이 올바르게 이루어지기 위해서는 역사적으로 어려운 프로그래밍 문제였습니다"는 문장이 맞지 않습니다. "author"를 "저자"로 옮기는 식의 직역도 보입니다.
- **라이선스**: 자체 라이선스(EXAONE AI Model License)라 사용 범위를 확인해야 합니다.

### translategemma-12b-it — 4B보다 낫지만 실수가 남음

Google의 Gemma 3 구조 번역 전용 모델 중 12B 크기입니다.

- **4B 대비**: "string literal"을 "문자열 리터럴"로 바르게 옮기는 등 용어 오류가 줄었습니다.
- **남은 문제**:
  - 문단 6 앞에 "다음은 영어 텍스트의 한국어 번역입니다:"라는 머리말을 붙였습니다.
  - 문단 6에서 "goes out of scope"를 "더 이상 사용되지 않을 때"로 옮겨 뜻이 달라졌습니다.
  - 문단 5에서 두 문장의 순서를 뒤바꿨습니다.
  - 문단 2에서 "on the heap"을 빠뜨렸습니다.
- **속도**: 한 쪽 34초로 hy-mt2-7b보다 느립니다. 같은 속도대에서 hy-mt2-7b가 더 정확하므로 고를 이유가 적습니다.

### translategemma-4b-it — 가장 빠르지만 초벌용

같은 계열의 4B 크기입니다.

- **속도**: 한 쪽 13초, 104자/초로 가장 빠릅니다.
- **문제**:
  - 문단 5에서 지시문까지 번역해 본문 앞에 붙였습니다.
  - "string literal"을 "문자 리터럴"로 옮겼습니다.
  - 문단 1의 마지막 문장은 뜻이 틀렸습니다.
  - 별도 시험에서 굵게·기울임 태그와 쪽 넘김 표시를 빠뜨렸고, `public`을 "공개"로 옮겼습니다.
- **용도**: 내용을 빠르게 훑어볼 때만 권합니다.

### 동작하지 않은 모델

- **YanoljaNEXT-EEVE-Rosetta-7B-2602** (`mradermacher`의 i1 Q4_K_M): 세 가지 요청 방식 모두에서 빈 줄만 한도까지 출력했습니다. LM Studio가 이 모델의 대화 형식을 맞게 적용하지 못한 것으로 보이지만 원인은 확인하지 않았습니다.
- **YanoljaNEXT-Rosetta-4B-2511** (`mradermacher`의 Q4_K_M): LM Studio가 모델을 올리다 실패했습니다("llama-server exited before becoming healthy"). 다른 양자화 파일은 시험하지 않았습니다.

두 모델 모두 이 환경에서 못 쓴 것이지, 모델 자체의 품질을 본 것은 아닙니다.

## 추천과 이유

1. **hy-mt2-7b를 기본으로 씁니다.** 속도와 품질이 함께 좋은 유일한 모델입니다. 4.6GB라 메모리 부담이 없고, 단순 방식 시험에서 강조 태그와 쪽 넘김 표시도 지켰습니다.
2. **정확도가 중요한 책이나 장은 qwen3.8-27b로 번역합니다.** 2.3배 느리지만 뜻을 놓치는 일이 가장 적고, 앞 문단 문맥을 받아 용어가 흔들리지 않습니다. 번역은 문단별로 저장되므로 중요한 부분만 이 모델로 다시 번역할 수 있습니다.
3. **속도가 최우선이면 EXAONE-3.5-7.8B를 씁니다.** translategemma-4b-it가 더 빠르지만 지시문이 섞이는 문제가 있어, 출력이 안정적인 EXAONE이 낫습니다.
4. **Rosetta 12B는 앱이 고유 형식을 지원하면 다시 볼 만합니다.** 지금 측정으로는 hy-mt2-7b와 비슷한 품질에 비슷한 속도라, 지원하더라도 기본 모델을 바꿀 이유는 아직 없습니다.

**원문**

> In the case of a string literal, we know the contents at compile time, so the text is hardcoded directly into the final executable. This is why string literals are fast and efficient. But these properties only come from the string literal’s immutability. Unfortunately, we can’t put a blob of memory into the binary for each piece of text whose size is unknown at compile time and whose size might change while running the program.

**qwen3.8-27b** (표준, 14.4초)

> 문자열 리터럴의 경우 컴파일 시점에 내용이 이미 알려져 있으므로, 해당 텍스트는 최종 실행 파일에 하드코딩되어 직접 포함됩니다. 이것이 문자열 리터럴이 빠르고 효율적인 이유입니다. 그러나 이러한 특성은 문자열 리터럴의 불변성에서만 비롯됩니다. 안타깝게도, 컴파일 시점에 크기가 알려지지 않고 프로그램 실행 중 크기가 변경될 수 있는 각 텍스트 조각에 대해 메모리 덩이를 바이너리에 넣을 수는 없습니다.

**hy-mt2-7b** (단순, 5.7초)
